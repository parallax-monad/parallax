# Parallax PRD | Hackathon MVP P0

## 1. Product Summary

**Parallax is a Moss-powered pre-transaction decision layer for Monad swaps.**

Before a user signs or retries after a failure, Parallax uses real execution evidence to help the user decide whether the current transaction should:

- **PROCEED**: no blocking evidence was found within the scope checked in this run;
- **ADJUST**: modify one relevant transaction condition and check again;
- **STOP**: stop the current path, or change the Route/Token Pair;
- **UNKNOWN**: the evidence is insufficient to reach a reliable conclusion for now.

Core statement:

> **Moss tells us what will happen. Parallax tells the user what to do next.**

The core of Parallax is not generating a longer Risk Report, nor is it determining that a transaction is "absolutely safe." It converts traceable execution evidence into a clear, actionable, and re-verifiable transaction decision.

---

## 2. Primary User

P0 adopts the following working assumption:

> A light DeFi user who performs basic Swaps on Monad and understands basic wallet and transaction operations, but cannot determine the cause of a failure or the correct adjustment.

P0 does not primarily target:

- complete beginners with no wallet or Swap experience;
- professional Traders;
- institutional users;
- Agent Builders;
- smart contract developers and debugging specialists.

This user profile is a product assumption for the hackathon and does not mean that full market validation has been completed.

---

## 3. Trigger Moment

The primary moment when Parallax intervenes is:

> The user has formed a Swap Intent and is about to sign, or is preparing to retry after a failure.

P0 does not cover:

- long-term protocol research or ratings;
- Portfolio analysis after a transaction is completed;
- an Agent automatically submitting transactions;
- automatic signing or broadcasting.

---

## 4. User Problem

A normal Swap page or raw Simulation often shows only a failure, Warning, or technical error. The user still cannot clearly answer:

- why it failed;
- whether the current problem concerns the Route, balance, parameters, or system integration;
- which adjustments are relevant to the problem;
- which changes will not resolve the current problem;
- whether the result actually changes after an adjustment;
- even if the transaction can execute, whether it meets the acceptance boundary the user explicitly declared.

### 4.1 Primary Problem | A

> After a Swap fails, the user does not know whether to modify Slippage, Priority Fee, Amount, Token Pair, or Route, and may therefore make repeated ineffective retries.

### 4.2 Optional Economic Boundary | B

`Minimum Received` is an acceptance boundary declared by the user, not a "safe threshold" automatically generated by Parallax.

Principles:

- the primary A flow does not require `minimumReceived`;
- the Economic Boundary Rule is enabled only when an explicit boundary exists;
- changing the Route or Amount may change the transaction result;
- lowering `minimumReceived` only relaxes the acceptance condition and does not mean that the result has improved;
- Parallax must not proactively advise the user to lower this boundary in order to produce `PROCEED`;
- P0 does not generate a "recommended safe threshold" based on AI, external market prices, or complex models.

The boundary source must be recorded as:

```ts
type BoundarySource =
  | "original_swap"
  | "user_declared"
  | "demo_preset"
  | "unavailable";
```

Where:

- `original_swap`: explicitly provided by the original transaction or original DEX Intent;
- `user_declared`: explicitly entered by the user;
- `demo_preset`: used only for clearly labeled Demo/Replay and must not be presented as a real user boundary;
- `unavailable`: no boundary is currently available, so the Economic Boundary Rule is not executed.

### 4.3 Conditional Fallback | E

> Simulation Success and Zero Warning do not mean that the economic result is necessarily acceptable.

E is enabled only when an explicit boundary exists. It serves as a second demo scenario or technical Fallback, does not change the Primary User, and is not positioned as an independent market proposition.

## 5. Product Goal

P0 must complete the following behavioral loop:

```text
Swap Intent
→ Moss Evidence
→ Cause classification
→ User Verdict
→ One relevant adjustment
→ One evidence-supported irrelevant adjustment
→ User modifies one condition
→ Re-run
→ Previous vs New Result
```

The success criterion for P0 is not coverage of every risk. It is the completion of at least one real, stable, explainable, and re-verifiable user decision loop.

P0 product form:

> **Wallet-style single-page Web App**

### Confirmed Boundaries

- no browser extension;

- no chat-style AI Agent as the primary interface;
- no signing;

Regardless of the final UX, the core check must be able to accept structured Intent directly without depending on natural language or wallet connection.

## 7. Core User Flow

```text
1. User enters a Swap Intent
2. User starts the pre-sign check
3. Parallax runs the Moss workflow
4. Parallax normalizes the evidence
5. Deterministic rules produce a decision
6. UI explains the cause and next action
7. User changes one relevant condition
8. Parallax re-runs the check
9. UI compares the previous and new result
10. Technical evidence remains available on demand
```

Every result must answer:

1. **What happened?**
2. **What proves it?**
3. **What can you change?**
4. **What will not help?**

---

## 8. Verdict Model

| Verdict | Product meaning | Expected user action |
|---|---|---|
| `PROCEED` | No blocking evidence was found within the scope checked in this run | Return to the original transaction flow or inspect the evidence |
| `ADJUST` | The current transaction conditions need to be modified, after which the check can be re-run | Modify one relevant condition and Re-run |
| `STOP` | The current path cannot execute or should not continue | Change the Route/Token Pair or stop |
| `UNKNOWN` | Reliable evidence is missing, so no trustworthy conclusion can be reached | Inspect the missing evidence; do not automatically allow the transaction |

### 8.1 Commitment Boundary of `PROCEED`

`PROCEED` does not mean:

- the transaction is absolutely safe;
- the protocol as a whole is reliable;
- the Token has no malicious risk;
- future prices will not change;
- Parallax recommends that the user make the transaction.

Recommended user-facing copy:

> **No blocking evidence found in the checked scope.**  
> No evidence preventing continuation was found within the scope checked in this run.

When an explicit economic boundary exists, the following may be added:

> **Meets your declared boundary.**  
> The current result meets the acceptance boundary you declared.

Do not use:

- `Safe to proceed`
- `Recommended`
- `Transaction is safe`
- any other expression implying that a complete safety review has been performed.

### 8.2 Scope Disclosure

The result must be able to express:

#### Checked

- Execution result;
- Moss warnings;
- the user's declared Minimum Received, if any.

#### Not Checked

- complete protocol security;
- complete malicious Token coverage;
- all asset semantics;
- future market changes.

#### Unknown

- critical evidence that is missing or unsupported in the current Run.

`Checked / Not Checked / Unknown` are required product semantics. They may be presented in the main result summary, Scope labels, or the Evidence Drawer; they are not required to be stacked together on the first screen.

## 9. System Failure Isolation

System state and User Verdict are separated at the data layer:

```ts
type SystemStatus =
  | "OK"
  | "INTEGRATION_ERROR";

type UserVerdict =
  | "PROCEED"
  | "ADJUST"
  | "STOP"
  | "UNKNOWN";
```

When Moss, RPC, or application services fail:

- do not generate a protocol `FAIL`;
- do not claim that the transaction is dangerous;
- return a retryable error or Replay;
- the UI must state that the check was not completed;
- whether `UNKNOWN` is also displayed may be decided by the final UX.

Core product principle:

> The system being unable to complete a check does not mean that the protocol or transaction is risky.

---

## 10. P0 Rule Groups

Rules must be deterministic, testable pure functions. An LLM may be used only for natural-language explanations or auxiliary Intent parsing and does not participate in the final decision.

### 10.1 Execution

At minimum, recognize:

- `SUCCESS`
- `NO_ROUTE`
- `REVERTED`
- `UNKNOWN`

System integration failures are not treated as protocol rule failures.

### 10.2 Economic Boundary

Execute only when an explicit boundary exists:

```text
expectedOutput >= minimumReceived
```

The output may state only whether the user's declared boundary is met. It must not state whether the transaction is "safe" or "a good deal."

### 10.3 Evidence Completeness

Check:

- whether a Moss Warning exists;
- whether there is a critical Asset Change that cannot be explained;
- whether fields required for a decision are missing;
- whether any data has an unknown source or cannot be reproduced.

### Rule Principles

- `UNKNOWN` is not equal to `PASS`;
- `UNKNOWN` also does not automatically mean protocol risk;
- Simulation Success does not automatically equal `PROCEED`;
- Zero Warning does not mean that the economic result is acceptable;
- Mock must not support the core Verdict;
- the Approval Rule runs only when a real Action includes Approval;
- Price Impact may enter a hard rule only after its data definition and comparability have been validated.

---

## 11. Frozen Behaviour Contract

Primary Scenario A must satisfy:

```text
One real, identifiable cause
→ One evidence-supported relevant adjustment
→ One evidence-supported irrelevant adjustment
→ User modifies one condition
→ Re-run
→ A new explicit result
```

The initial Reason-to-Action Mapping is only a hypothesis to be validated:

| Cause | Required evidence | Potentially relevant adjustment | Usually irrelevant adjustment | Expected verdict |
|---|---|---|---|---|
| No Route | Moss Quote/Action | Route, Token Pair | Priority Fee, blindly increasing Slippage | STOP |
| Output below boundary | Quote/Outcome + explicit boundary | Route, Amount | Gas | ADJUST |
| Balance/Transfer Failure | Moss + RPC balance query | Amount, Balance | blindly increasing Slippage | ADJUST/STOP |
| Moss Warning | Simulation/Receipt | Depends on the specific Warning | Do not guess without evidence | ADJUST/UNKNOWN |
| Missing Evidence | List of missing fields | Supplement the data or change the scenario | Allowing the transaction directly | UNKNOWN |

Any mapping that ultimately enters product logic must be validated using real Moss/RPC evidence.

## 12. Adjustable Parameters

Candidate adjustable parameters:

- Amount;
- Token Pair;
- Route/Protocol;
- Slippage;
- Minimum Received.

Of these:

- Amount, Token Pair, Route/Protocol, and Slippage are transaction conditions;
- Minimum Received is the user's acceptance boundary;
- the system must not describe lowering Minimum Received as improving the transaction result.

The frontend must not assume that all parameters are editable for every cause. The API should return suggestions corresponding to the cause:

```ts
type ActionSuggestion = {
  field:
    | "amountIn"
    | "tokenPair"
    | "protocol"
    | "slippage"
    | "minimumReceived";
  category:
    | "TRANSACTION_CONDITION"
    | "ACCEPTANCE_BOUNDARY";
  relevance:
    | "RELEVANT"
    | "IRRELEVANT"
    | "UNKNOWN";
  reason: string;
};
```

The final editable fields are frozen by the technical team based on the validated Reason-to-Action Mapping.

## 14. Moss Integration Boundary

### Moss is responsible for

- `discover`
- `load`
- `action`
- `simulate`
- the ability to construct an unsigned transaction;
- returning Receipt, Warnings, Changes, Outcome, and an available Revert Reason.

### Moss is not responsible for

- determining whether the user accepts the result;
- recommending what the user should modify;
- automatic signing;
- automatic broadcasting;
- forming Parallax's final User Verdict.

### Parallax is responsible for

- saving the original Intent;
- calling Moss;
- normalizing Moss Raw Output;
- supplementing with an RPC Query when necessary;
- executing deterministic Rules;
- generating a Decision;
- supporting Adjust & Re-run;
- isolating Integration Error.

Core flow:

```text
Intent
→ Moss discover
→ Moss load
→ Moss action
→ Moss simulate
→ Normalized Evidence
→ Rule Engine
→ User Decision
→ Receipt
```

The frontend and Rule Engine should not depend directly on Moss raw types.


### 15.2 Primary Scenario A Fixture

The specific Token Pair, Sender, failure cause, and adjustment parameter for A are selected by the technical team based on real reproducibility.

A does not have to use `MON → USDC`.

The technical team may use:

- `NO_ROUTE`
- Transfer Failure
- another real cause that Moss can identify and explain consistently

However, it must satisfy the Frozen Behaviour Contract in Section 11.

### 15.3 PancakeSwap

PancakeSwap does not block Kuru P0.

It enters formal P0 only when:

- the real flow is stable;
- field sources are complete;
- integration failures can be isolated;
- it does not block Kuru;
- it adds clear value to E or the user decision.

Otherwise, it is reduced to `UNAVAILABLE`, P1, or Stretch.

## 16. Reference API Contract

The following is the minimum reference shape required by the product. The final internal routes and Schema are frozen by the technical team:

```text
POST /api/check
GET  /api/replay/:id
```

Re-run may continue to call `/api/check` with `parentRunId`.

```ts
type CheckSwapInput = {
  parentRunId?: string;
  sender?: string;
  recipient?: string;
  protocol: "kuru" | "pancake";
  tokenIn: string;
  tokenOut: string;
  amountIn: string;
  minimumReceived?: string;
  minimumReceivedSource?: BoundarySource;
  slippage?: string;
};

type CheckSwapResult = {
  runId: string;
  parentRunId?: string;

  systemStatus: "OK" | "INTEGRATION_ERROR";
  verdict: "PROCEED" | "ADJUST" | "STOP" | "UNKNOWN";

  summary: string;
  recommendedActions: ActionSuggestion[];
  irrelevantActions: ActionSuggestion[];

  checked: string[];
  notChecked: string[];
  evidence: EvidenceItem[];
  ruleResults: RuleResult[];
  unknowns: UnknownItem[];

  diff?: RunDiff;
  replayMode: boolean;
};
```

All BigInt values crossing the API must be serialized as string.

## 18. Smart Contract Boundary

P0 does not add a self-developed smart contract.

The Onchain component comes from:

- a real Kuru smart contract Action constructed by Moss;
- a real Simulation of an unsigned transaction;
- Monad onchain Quote, Receipt, and Asset Change Evidence.

- Receipt Registry;
- onchain Risk Verdict;
- user signing;
- Swap broadcasting;
- Token Custody;
- a self-developed transaction execution contract.

## 19. Functional Requirements

### FR-01 | Intent Capture

The system can receive a structured Swap Intent and convert it into a unified internal format.

### FR-02 | Moss Execution Evidence

The system can complete at least one real Kuru Quote, Action, Simulation, and Receipt retrieval.

### FR-03 | Evidence Normalization

The system converts Moss and necessary RPC data into structured Evidence that does not depend on Moss raw types.

### FR-04 | Deterministic Decision

The system uses deterministic rules to produce PROCEED, ADJUST, STOP, or UNKNOWN.

### FR-05 | Scope-aware Explanation

The system explains what happened, what the evidence is, what can be changed, what will not help, and states Checked, Not Checked, and Unknown.

### FR-06 | Adjust & Re-run

The user can modify one relevant condition and execute the check again.

### FR-07 | Result Diff

The system displays the key changes between the Previous and New Result.

### FR-08 | Evidence Access

The user can expand Evidence on demand instead of viewing complete Raw Data on the main page by default.

### FR-09 | Failure Isolation

Moss, RPC, or application integration errors must not be presented as protocol risk.

### FR-10 | Replay

The core Demo can load a clearly labeled real recorded Fixture if the live call fails.

### FR-11 | Boundary Integrity

The Economic Boundary Rule executes only when an explicit Minimum Received exists, and the system must not recommend lowering the boundary to manufacture PROCEED.

---

## 20. Non-functional Requirements

- core decisions are testable and reproducible;
- the core Verdict does not depend on an LLM;
- Mock must not be presented as real onchain evidence;
- real data records its source and block where possible;
- Unknown must not be silently converted to Pass;
- Integration Error is separated from protocol risk;
- the frontend must not depend directly on Moss Raw Type;
- P0 does not require a persistent history database;
- P0 does not introduce a complex Queue or SSE in advance;
- the primary flow must be suitable for a demonstration within three minutes;
- target completion date: **2026-08-05**.

## 21. P0 Acceptance Criteria

P0 is achieved when:

1. At least one real Kuru Swap Intent can complete Moss Quote → Action → Simulation;
2. Moss Evidence can be normalized into a unified data structure;
3. At least one real A scenario can produce an explicit cause;
4. The scenario includes one evidence-supported relevant adjustment;
5. The scenario includes one evidence-supported irrelevant adjustment;
6. The user can modify one condition and Re-run;
7. The UI can display the Previous and New Result;
8. The system can return PROCEED, ADJUST, STOP, or UNKNOWN;
9. PROCEED is not expressed as absolute safety or a transaction recommendation;
10. The UI can express Checked, Not Checked, and Unknown;
11. Integration Error is not presented as protocol risk;
12. Unknown is not automatically allowed;
13. All core evidence is not Mock;
14. Replay Fixture is explicitly labeled as Replay;
15. The Economic Boundary Rule executes only when an explicit boundary exists;
16. The product does not sign, broadcast, or take custody.

## 23. Frozen Decisions, Implementation Gates and Post-hackathon Validation

### 23.1 Frozen Product Decisions

- the Primary User uses the current light DeFi user working assumption;
- A is the Primary Problem;
- B is an optional economic boundary and its source is recorded;
- E is a conditional Fallback that depends on an explicit boundary;
- PROCEED means only that no blocking evidence was found within the checked scope;
- the product is a wallet-style single-page Web App;
- P0 completes one relevant adjustment and Re-run;
- Moss Trace is collapsed by default;
- no signing, broadcasting, or custody;
- no self-developed smart contract is added;
- PancakeSwap does not block Kuru.

### 23.2 Required Implementation Validation

The technical team will freeze the following in implementation, the shared Contract, tests, a PR, or an ADR:

- the specific real Fixture for A;
- Moss version/commit;
- RPC, Sender, and Token Address;
- final API, Receipt, and Evidence Schema;
- the internal error structure for Integration Error;
- Error Mapping;
- BigInt serialization implementation;
- Replay Fixture format;
- Timeout/Retry;
- Evidence Drawer technical fields;
- technical availability of Price Impact and Approval;
- PancakeSwap Go/No-Go.

These items do not block the start of product development.

### 23.3 Non-blocking UX Decisions

Product, UX, and technical implementation will jointly converge on:

- whether natural language enters Stretch;
- whether Wallet Connect enters P0;
- final Primary CTA copy;
- Evidence Drawer information hierarchy;
- page presentation of Integration Error;
- which validated parameters are editable in the corresponding scenarios.

### 23.4 Post-hackathon Validation

The following are not prerequisites for development in this cycle:

- the real frequency of the target problem;
- whether users are willing to add a pre-sign check;
- whether the product will eventually use a wallet extension, DEX embed, or another entry point;
- more complete market and user validation;
- whether to expand to complex Policies, protocol ratings, or more Actions.
